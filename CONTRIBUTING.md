# Contributing to ClaudeDesk

Thanks for helping. Bug reports, ideas and pull requests are all welcome. For anything bigger than a small fix, open an issue first so we can agree on the approach.

## Development setup

You need Python 3.10 or newer. The tray app and the exe build need Windows; the data layer, the CLI and the web UI (`--serve`) run anywhere.

```bash
git clone https://github.com/tsljgj/ClaudeDesk.git
cd ClaudeDesk
python -m venv .venv && .venv\Scripts\activate      # or: source .venv/bin/activate
pip install -r requirements.txt -r requirements-dev.txt
python -m playwright install chromium               # for the UI tests and screenshots
```

Run from source against a scratch data folder, so you never touch your real inbox:

```bash
cd src
python -m claudedesk --data ../.dev-data             # tray + window (Windows)
python -m claudedesk --serve --data ../.dev-data     # local server only; open the printed URL in a browser
```

Post test messages from another terminal:

```bash
python desk.py --data .dev-data post --kind decision --session demo --title "Pick one?" \
    --body "Some **Markdown**" --option "A::first" --option "B::second" --no-launch
python desk.py --data .dev-data listen --session demo --timeout 60
```

Outside a Claude Code session there is no `CLAUDE_CODE_SESSION_ID`, so pass `--session` yourself; the card then shows the session as open until `listen` runs. The session protocol is described in [docs/PROTOCOL.md](docs/PROTOCOL.md).

`build.cmd` builds a one-file `ClaudeDesk.exe` with PyInstaller (it reports build 0 and never updates itself).

## Tests

```bash
python -m pytest -q
```

- `tests/test_store.py`, `test_desk.py`, `test_followups.py`, `test_protocol.py`, `test_round4_backend.py`, `test_server.py` and `test_icon.py` are plain Python.
- `tests/test_protocol.py` covers session protocol v2: it runs real `desk.py` subprocesses (`post`, `listen`, `close --mine`, `status`, `inbox --adopt`, legacy `wait`) and checks batching, exactly-once delivery and the app's session states. `--body-from-chat` / `--question-from-chat` are tested against synthetic transcripts, never your real ones.
- `tests/conftest.py` removes `CLAUDE_CODE_SESSION_ID`, `CLAUDE_PID` and `CLAUDE_CONFIG_DIR` from the environment for every test, so the suite behaves the same when you run it from inside a Claude Code session (otherwise every test message would be recorded as that session's). Tests that need a session set these variables themselves.
- `tests/test_ui*.py` and `test_round4_integration.py` start a real `Store` and local server and drive the UI in Chromium through Playwright. They are skipped when Playwright isn't installed.
- On Windows you can skip the Chromium download and use Edge: `CHROMIUM_PATH="C:/Program Files (x86)/Microsoft/Edge/Application/msedge.exe" python -m pytest -q`.
- CI runs the whole suite on Ubuntu with Playwright's Chromium, then on Windows runs the store tests, builds the exe, self-tests it and runs an end-to-end check (post with `desk.py`, reply through the app, self-update).
- UI tests must wait for state (`wait_for_function`, `wait_for_selector`) rather than sleep; CI machines are slower than yours.

Add or update tests with every behaviour change.

## Code style

- **Language.** The UI, code comments, docstrings and the Claude Code skill are in Simplified Chinese; the READMEs are in English and Chinese and are kept in parity. Write new comments in Chinese, short, and explain *why* rather than *what*.
- **Python.** 3.10+, type hints where they help. `desk.py` uses the standard library only, because sessions run it with whatever Python they have. `store.py` must not import GUI libraries.
- **Front end.** Plain ES5-style JavaScript (`var`, `function`, no arrow functions, no modules) in a single IIFE; there is no build step. All colors and sizes go through the CSS custom properties on `:root` in `app.css`; themes, accents, density and reading width only change variables.
- **Vendored libraries** under `src/claudedesk/assets/vendor/` are generated by `scripts/vendor.py`. Don't edit them by hand.
- `.editorconfig` sets encoding, line endings and indentation (4 spaces for Python and PowerShell, 2 for JS, CSS, HTML, YAML, JSON and Markdown).

## Privacy in tests, docs and screenshots

Never put real inbox content, personal paths, account names or real project names into tests, docs, issues or screenshots. Use placeholders such as `webapp`, `acme-data-pipeline`, `示例项目` and `my-project`.

The README screenshots come from demo data, not from a real inbox. To regenerate them after a UI change:

```bash
python scripts/screenshots.py            # writes docs/screenshot-light.png and docs/screenshot-dark.png
```

## Commits and pull requests

- One topic per pull request. The subject line says what changed for the user, in the imperative ("Show wait times on waiting rows"); add a body if the reason isn't obvious.
- Don't add AI attribution trailers (`Co-Authored-By: Claude …`, `Claude-Session: …`, "Generated with Claude Code"). The repo's `.claude/settings.json` turns them off for Claude Code.
- For UI changes, attach before/after screenshots made with demo data.
- If you change the CLI, the reply format or the session protocol, update `skill/claude-desk/SKILL.md`, `docs/PROTOCOL.md` and both READMEs.
- User-facing changes get a line in `CHANGELOG.md`.

## How releases work

- Every push to `main` runs CI. When it is green, CI publishes a GitHub release tagged `build-<N>` (`N` is the workflow run number) with `ClaudeDesk.exe` and `ClaudeDesk.exe.sha256`, and marks it latest. The release notes are the subject lines of the commits since the previous build.
- Installed apps poll the latest release and update themselves to it, so **everything merged to `main` ships to users**. Other branches and pull requests are built and tested but never released.
- Never force-push `main`. The `build-<N>` tag format is parsed by the updater (`src/claudedesk/update.py`); changing it would strand every installed copy.
- The app version (`src/claudedesk/__init__.py` and `packaging/version.txt`, bumped together) changes when a set of builds adds up to a release worth naming; record it in `CHANGELOG.md`.

## Reporting security issues

Please don't open public issues for vulnerabilities. See [SECURITY.md](SECURITY.md).
